# PDF Signature Verification (TCASFolio)

Investigation notes and decisions for verifying the digital signature on
**TCASFolio** portfolio PDFs uploaded by applicants. This is **not** a general
check for all uploads: it is meant to be switched on only for specific
`ProjectUploadedDocument` slots (the ones that take TCASFolio PDFs), by setting
the slot's `validator` to `'tcasfolio'` (see
[Custom validators](uploaded-documents.md#custom-validators)). The check itself
is `appl/pdfsignatures/verify.py`; the validator is
`appl/document_validators/tcasfolio.py`.

The findings below come from one sample TCASFolio PDF (downloaded 2026-09),
inspected on 2026-09-13 using only its signature/certificate structure (no
page content was read — the files contain personal information). Re-check
against more samples before relying on details that may vary.

## Decisions (current)

1. **Bundle the trusted roots** in the project — both **Thailand NRCA G1 and
   G3** — as PEM files committed to the repo with pinned SHA-256 fingerprints
   (see [Storing the trust roots](#storing-the-trust-roots)). Do not use the
   system trust store or the certificates embedded in the PDF as trust
   anchors.
2. **Pin the signer** to the current TCASFolio signer found in the sample
   (ทปอ., `organizationIdentifier=TIN-0993000086848`, see below). A valid chain
   alone is not enough — any organization holding a certificate from a Thai
   CA would pass.
3. **No revocation check (OCSP/CRL) for now**, and no network access at all
   during the check. Revocation can be done later as a batch check over
   stored uploads.
4. **Validate minimally, at the current time** (not the self-asserted signing
   time — the file is signed at download anyway). See
   [Verification steps](#verification-steps-what-the-check-does).
5. **Upload-time accept/reject only.** A failing file is rejected with a
   message; nothing is stored on `UploadedDocument`, there is no "record only"
   mode, existing uploads are not re-checked, and staff see nothing extra.
6. **Fail closed.** An unknown validator key or an exception during the check
   rejects the upload (logged) with a "try again / contact staff" message.
7. **Size limit** is the slot's ordinary `size_limit` (samples are ~4.7 MB, so
   raise it on TCASFolio slots); the validator does not check size.
8. **TCASFolio links** (for url/any slots) are accepted as-is until the URL
   pattern is known (`validate_url()` in `appl/document_validators/tcasfolio.py`).

## What a TCASFolio PDF looks like

- Generated by headless Chrome (`Producer: Skia/PDF`), then signed as an
  **incremental update** (two `%%EOF`s).
- One signature field: `/Filter /Adobe.PPKLite`, `/SubFilter
  /adbe.pkcs7.detached`, CMS `SignedData` (detached), SHA-256 digest,
  RSA PKCS#1 v1.5.
- `/ByteRange` covers the **whole file** (nothing appended after signing).
- Signed attributes: `content_type`, `signing_time`, `message_digest` only.
- The CMS embeds the **full chain** (signer, intermediate, root).
- **Not present:** RFC 3161 timestamp token, `/DocTimeStamp`, `/DSS`
  (embedded revocation info / LTV), `/DocMDP` certification. So the
  `signing_time` is self-asserted, and long-term validation after the signer
  certificate expires is not possible.
- **The PDF appears to be signed at download time**: the sample's signing time
  was 2026-09-12, while the timestamp in its filename was from 2024-10. The
  signing time therefore says when the file was downloaded, not when the
  portfolio was made.
- Sample size was ~4.7 MB — larger than the default
  `ProjectUploadedDocument.size_limit` (2,000,000).
- The signature carries no applicant identifier; tying a signed PDF to a
  specific applicant is a separate problem.

### Roots to bundle

| Root | Validity | SHA-256 |
|---|---|---|
| Thailand National Root Certification Authority - G1 | 2013-03-27 → 2036-03-27, RSA 4096 | `2A8DA2F8D23E0CD3B5871ECFB0F42276CA73230667F474EEDE71C5EE32CC3EC6` |
| Thailand National Root Certification Authority - G3 | 2023-08-17 → 2043-08-12, RSA 4096 | `3D2794A0539486A83E8032CF14FE886553E52239CBAEC1B9CFEF5595ADBBF444` |

Both are bundled.

- **G1** is what the sample chains to. Source:
  `https://www.nrca.go.th/cert/nrca/THNRCA.der`.
- **G3** is not used by the sample, but it is ETDA's newer root (Document
  Signing only in Microsoft's program); future signer certificates may chain to
  it. Subject `C=TH, O=Electronic Transactions Development Agency, CN=Thailand
  National Root Certification Authority - G3`. No direct download was found on
  `www.nrca.go.th` (the obvious `.der` paths 404); it was fetched from
  `https://crt.sh/?d=<SHA-256>` and authenticated by matching the SHA-256
  against Microsoft's CCADB listing (below).

**How the G1 root was authenticated** (independently of the PDF):

- Downloaded over HTTPS from `www.nrca.go.th` (TLS verified); fingerprint
  matches the root embedded in the PDF.
- Listed as **Included** in Microsoft's Trusted Root Program
  (CCADB report `IncludedCACertificateReportForMSFTCSV`) with the same SHA-256,
  EKUs including *Document Signing*.
- **Not** in the Mozilla/Ubuntu CA bundle (`/etc/ssl/certs`), so default
  Python/OpenSSL trust will not validate these PDFs — hence bundling.

**How the G3 root was authenticated:** the certificate from crt.sh has the
SHA-256 listed for *Thailand National Root Certification Authority - G3* in the
same Microsoft CCADB report (status **Included**, EKU *Document Signing*).

When adding the root files to the repo, verify their SHA-256 against the table
above.

## Storing the trust roots

**Decision: commit the root certificates to the repo as PEM files, with their
SHA-256 fingerprints pinned in code.**

Why the repo:

- They are **public certificates, not secrets** — no need for
  `settings_local.py`, env vars, or S3.
- **Changes are code-reviewed.** Adding or replacing a trust anchor is a
  security decision; a git diff makes it visible and revertable.
- **Every environment trusts the same roots** (dev, tests, production), with
  no deployment step to forget.

Rejected alternatives:

- **Database / Django admin** — anyone with admin access could add a root CA
  and the check would accept PDFs signed under it.
- **Fetching from nrca.go.th at runtime** — network dependency, and defeats
  pinning.
- **System store / `certifi`** — NRCA is not in it, and OS updates can change
  it.

Layout (implemented — `appl/pdfsignatures/profiles.py` has `PROFILES`,
`load_trust_roots(profile_name)` returning the roots' DER bytes, and raises
`TrustRootError` on a fingerprint mismatch or unknown profile; tested by
`appl.tests.TrustRootsTestCase`):

```
appl/pdfsignatures/
    __init__.py
    profiles.py              # TCASFOLIO profile: root files + fingerprints + signer pin
    trust_roots/
        README.md            # per root: source URL, date retrieved, SHA-256,
                             # how it was authenticated, expiry
        thailand-nrca-g1.pem
        thailand-nrca-g3.pem
```

```python
TCASFOLIO = {
    'roots': [
        ('thailand-nrca-g1.pem',
         '2A8DA2F8D23E0CD3B5871ECFB0F42276CA73230667F474EEDE71C5EE32CC3EC6'),
        ('thailand-nrca-g3.pem',
         '3D2794A0539486A83E8032CF14FE886553E52239CBAEC1B9CFEF5595ADBBF444'),
    ],
    'signer': {
        'organization_identifier': 'TIN-0993000086848',
        'organization_name': 'Association of The Council of University Presidents of Thailand',
    },
}
```

Rules:

- **Fingerprint check on load** — loading a profile computes each file's
  SHA-256 and raises if it does not match. A file edited by accident or
  swapped fails loudly, and changing a root means changing the file and the
  code in the same commit.
- **A unit test loads every profile**, so a mismatch fails in tests before it
  reaches production.
- **Slots refer to a profile by name.** `ProjectUploadedDocument` stores a key
  such as `'tcasfolio'`, never certificates. Staff choose *which* check applies,
  not *what it trusts*.
- **No intermediates in the bundle.** INET CA - G1 comes from the PDF and only
  has to chain to a bundled root. If some PDFs turn out to omit it, add it
  later as an untrusted helper certificate, never as a trust anchor.

Upkeep:

- G1 expires **2036-03-27**; G3 expires **2043-08-12** (note these in the
  `trust_roots/README.md`).
- A new TCASFolio signer organization or CA is a code change to the profile,
  on purpose.

## Verification steps (what the check does)

Implemented in `appl/pdfsignatures/verify.py` with **pyHanko** (0.37, +
`pyhanko-certvalidator`; installed without changing the `cryptography` /
`asn1crypto` pins). `verify_pdf_signature(pdf_bytes, trust_roots_der,
signer_pin)` returns `SignatureCheck(ok, code)`; `verify_with_profile(pdf_bytes,
'tcasfolio')` supplies the bundled roots and pin. In order:

| # | Step | Failure code |
|---|---|---|
| 1 | Read the PDF (`PdfFileReader`, non-strict) | `not_pdf` |
| 2 | Exactly one embedded signature | `not_signed` |
| 3 | `validate_pdf_signature` → coverage is `ENTIRE_FILE` (ByteRange covers the whole file) | `modified_after_signing` |
| 4 | … `intact` and `valid` (message digest + CMS signature) | `signature_invalid` |
| 5 | … `trusted`: path signer → embedded intermediate → **bundled root**, validity at **now**, key usage `digital_signature` or `non_repudiation` | `untrusted_signer` |
| 6 | Signer subject `organization_identifier` + `organization_name` match the pin | `untrusted_signer` |

The `ValidationContext` has only the bundled roots as trust anchors,
`allow_fetching=False`, and a `NO_CHECK` revocation policy for both the signer
and intermediates. Diff analysis is skipped (step 3 already rejects any
incremental update after the signature). Expired certificates also come out as
`untrusted_signer`. Any unexpected exception propagates, and the validator
runner turns it into `verification_error`.

Tests (`appl.tests.PdfSignatureVerifyTestCase`) sign a blank PDF with a
throwaway root → intermediate → signer chain generated at test time. The real
sample is not committed (personal data); `TcasfolioValidatorTestCase` checks it
only when `TCASFOLIO_SAMPLE_PDF=/path/to/file.pdf` is set.

## Results on the sample (2026-09-13)

| Check | Result |
|---|---|
| ByteRange covers whole file | ✅ |
| Message digest matches | ✅ |
| CMS signature valid | ✅ |
| Chain to bundled G1 root (`openssl verify -x509_strict`), now and at signing time | ✅ |
| Chain without intermediate (negative test) | ❌ as expected |
| OCSP signer @ INET (response signature verified) | good |
| OCSP INET CA @ NRCA (response signature verified) | good |
| NRCA ARL (valid to 2027-01-21): INET CA serial listed? | no |

Revocation was checked once during the investigation only; per the decisions
above it is not part of the upload-time check.
